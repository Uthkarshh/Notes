# 1. Prioritized UX audit

[Design index](README.md) · [Tokens](02-design-system.md) · [Screen specifications](03-screen-specs.md) · [Roadmap](04-roadmap.md)

The app has a sound information architecture and considerable functional coverage. The main friction comes from inconsistent persistence, tall control stacks, and actions that require navigating away from the thing being acted on. Prioritize trust and recurring tasks before visual flourish.

## Ranking

**P0** is a release gate for the redesigned editor because it affects confidence that edits persist. **P1** affects a frequent core task or makes an action materially harder. **P2** improves secondary tasks or visual/adaptive quality. These are heuristic priorities, not measured incident rates. Effort is relative: S = localized change; M = coordinated screen/state/repository work; L = shared infrastructure or substantial interaction work.

## Findings that change the implementation plan

The README describes individual **or bulk** Inbox filing. The checked UI provides individual filing only. The repository already accepts `List<Long>`, so batch filing needs selection state, transactional behavior and Undo rather than a new underlying concept.

Voice is already visible as **Use voice** inside Quick Capture, and Today's FAB already has an accessible long-click label. Improve this affordance and make it consistent; do not count voice capture as missing functionality. Actual offline transcription depends on the installed Android recognizer. Typed capture is the dependable offline fallback.

AMOLED is also implemented: `toAmoled()` sets black root surfaces and `#0A0A0A`–`#202020` containers. The work is to make components use these levels coherently and to audit boundaries/contrast, rather than inventing another theme mode.

Metadata application currently preserves title and personal notes in its repository path. The diff preview should make that guarantee visible and protect other populated metadata fields too. **Director is not present in `ItemMetadata` or the current TMDB mapping**; offering it in the proposed preview requires extending the model, codec and provider response mapping.

App Lock already guards activities, sets secure window flags, hides notification content, and redacts the fact widget whenever the feature is enabled. Backups already expose last-success information and support encrypted archives with covers. The redesign should improve clarity and preserve those behaviors. App Lock uses biometrics or the Android device PIN/pattern/password; a separate app-specific PIN is not implemented.

## Code risks to resolve while redesigning

These are source-based risks, not newly reproduced failures:

- `MetadataEditor` keys its local fields by `raw`. A metadata update can reinitialize the form while an edit is in progress. A single draft must merge repository acknowledgements without replacing dirty fields.
- A delayed full-metadata snapshot can overwrite a later enrichment change even though core `saveDetails` currently preserves inline workflow controls. Use field patches and revision-aware merging.
- Removing the explicit metadata save without retaining incomplete numeric input would silently turn intermediate input into missing values. Treat raw drafts separately from validated domain values.
- A delete snackbar cannot be implemented safely by calling the current hard delete and recreating only the item. Delete also removes links, tags, FTS and cascading history. Provide a reversible deletion boundary.
- Completing several items can trigger multiple reflection requests; the global completion UI currently holds one request. Queue requests by completion event and let batch actions defer reflections.
- Lookup consent is a stored setting enforced in `MetadataLookup`. Contextual consent must finish persisting before Search runs; network consent alone cannot supply the required TMDB token.

## Acceptance priorities

First establish that mixed edits survive Back/backgrounding and that status/metadata operations cannot overwrite each other. Then establish that a due item can be handled from Today, ten captures can be filed as one batch, and a person can draw from Discover without expanding advanced filters. Visual targets and proposed performance/task-time targets are specified in the [roadmap](04-roadmap.md); they need validation with users and devices.
